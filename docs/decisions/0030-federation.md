# ADR 0030: ActivityPub federation, limited v1

- Status: accepted (2026-10-27; the maintainer accepted the recommended answers, see
  [Decisions at acceptance](#decisions-at-acceptance-2026-10-27))
- Date: 2026-10-27 (code checked at `ccf9c17`)

## Context

Milestone N4 (`.claude/briefs/next/N4-federation.md`, batch 6 with W3 and N3) lets a Mastodon user,
or anyone on an ActivityPub server, follow `@channel@instance` and see a post when the channel goes
live and when a VOD or clip is published. Two CommonAir instances can follow each other's channels
the same way. Watching and chat stay on the home instance. feature-wins.md parks "ActivityPub
actor and Move" until this unit and its trust and safety design exist
(`docs/product/feature-wins.md:777`, `:1043`).

What the code has today:

- **Nothing federated.** No WebFinger, actor, inbox or NodeInfo code exists; there is no
  `services/api/src/federation/` directory.
- **The events N4 needs are partly there.** `stream.online` (`packages/contracts/src/events.ts:75`)
  is written when a broadcast starts (`services/api/src/media/hooks.ts:120-126`), and N1 builds the
  go-live fan-out on it ([ADR 0028](0028-notifications.md) decision 8). `channel.update` carries the
  `mature` label (`packages/contracts/src/events.ts:89-103`). `moderation.restriction` is an
  internal event for a T1 restriction of a live broadcast (`:576-583`). There is no event for a VOD
  or clip becoming public. A channel is suspended in several places (a case decision,
  `services/api/src/routes/moderation.ts:185-203`; `setSuspension`,
  `services/api/src/moderation/suspension.ts:62`; the T0 path,
  `services/worker/src/moderation/t0.ts:96-105`), and none writes an event saying so: the case
  decision emits the internal `moderation.case.resolved`, whose payload has no channel-suspended
  field (`packages/contracts/src/events.ts:562-575`).
- **Internal events have no consumer.** The relay validates internal rows and marks them published
  without putting them on the bus or enqueueing anything (`services/worker/src/outbox.ts:82-94`), so
  reacting to `moderation.restriction` or a new suspension event needs a relay change.
- **Media rows say what is public.** `vods.visibility` defaults to public and VODs and clips both
  have a status, a `thumbnailKey` and a `removedReason` (`packages/db/src/schema/media.ts:138-197`).
  Clips record the viewer who made them in `creatorId` (`:180`).
- **Outbound delivery has the pieces.** The outbox relay claims rows with `FOR UPDATE SKIP LOCKED`
  and publishes them (`services/worker/src/outbox.ts:4-11`); `resolveCallback` pins a public
  address against SSRF and rebinding (`services/worker/src/webhooks/ssrf.ts:162-200`);
  `postWebhook` sends through it (`services/worker/src/webhooks/http.ts:29-40`); retries use
  `DEFAULT_BACKOFF_MS` of 1, 5, 30 and 120 minutes (`services/worker/src/webhooks/backoff.ts:7`).
  The guard lives in the worker; the API has no equivalent for outbound fetches.
- **Secrets at rest** use `encryptSecret` (AES-256-GCM per purpose,
  `packages/tokens/src/secrets.ts:30`).
- **Every admin action writes `audit_log`** (AGENTS.md), which is append-only by trigger
  (`packages/db/drizzle/0001_protections.sql:105`).

Two facts make the scope easy to keep small: there are no self-hosters or public instance, so the
actor URL scheme can be chosen now and never migrated, and federation is new, so there is no
remote state to keep compatible.

## Decisions

### 1. Scope v1: channels publish, nothing else federates

Each channel that opts in is an actor that publishes. Local users are not actors: no federated
chat, no federated follows by local users, no remote replies shown anywhere, no likes or boosts
counted. The inbox handles `Follow`, `Undo{Follow}` and `Delete` of an actor, and accepts and
ignores everything else (decision 5).

Why limited: inbound replies, mentions and follows from other servers bring moderation load
(reports from and about people on servers we do not run, spam, harassment by reply) that the
instance has not staffed for. Publishing outward, with followers we can drop, carries almost none
of it.

Federation is off unless the operator sets `FEDERATION_ENABLED` (new, default false,
`packages/config/src/env.ts` and `.env.example`), and then off for each channel until its
streamer turns it on in the studio.

### 2. Actors and identifiers

- The actor type is `Service`: the posts are generated by the platform, and Mastodon shows
  `Service` actors as automated, which is honest.
- The actor id is stable and built from the channel id (`https://<domain>/ap/channels/<uuid>`),
  so a slug change does not orphan followers. `preferredUsername` is the slug; WebFinger maps
  `acct:<slug>@<domain>` to the id. The domain comes from `instanceSite()` (rule 5).
- The actor document carries the display name, description, avatar and banner (public URLs),
  a link to the channel page, `inbox`, `outbox` (public posts only), `followers` as a collection
  that reports a count and no items (decision 8), and `publicKey`.
- NodeInfo 2.1 publishes software name and version, `activitypub` as the protocol and whether
  registrations are open; `usage` carries no user counts.

### 3. Objects: `Note` for go-live, `Video` for VODs and clips, linking home

- **Go-live:** `Create{Note}` addressed to Public and the followers collection, with the title,
  the category, a link to the channel page and the current thumbnail as an attachment.
- **VOD or clip made public:** `Create{Video}` with the title, duration, thumbnail and a `url`
  pointing at the watch page on the home instance. Media is never pushed, and no stream URL is
  put in the object. Only public VODs and clips federate; subscriber and private ones never do.
- **Clips are attributed to the channel actor only.** `clips.creatorId` is a local user, and local
  users do not federate (decision 1), so the clipper is not named.
- **Removal sends `Delete`.** When a federated VOD or clip is removed, expired, DMCA-disabled or
  made non-public, the worker sends `Delete` with a `Tombstone`. A T1 restriction of a live
  broadcast (`moderation.restriction`) deletes its go-live Note.

Objects are JSON with the ActivityStreams context (`https://www.w3.org/ns/activitystreams` plus the
security vocabulary for `publicKey`), built and parsed as plain JSON. There is no JSON-LD
processing: we emit a fixed shape and read only the fields we need from known shapes. All text in
objects is the streamer's own (title, description) or comes from the i18n catalog.

### 4. HTTP Signatures (draft-cavage) with per-actor keys, encrypted and rotated

Every delivery is signed with draft-cavage HTTP Signatures over `(request-target)`, `host`,
`date` and `digest` (SHA-256 of the body), the scheme Mastodon and most of the fediverse verify.
Keys are RSA-2048 (RSASSA-PKCS1-v1_5 with SHA-256), because that is what those servers accept;
Web Crypto generates and uses them, so there is no new dependency.

- Each channel actor has its own key pair, created when the channel turns federation on. The
  private key is stored with `encryptSecret` under a federation purpose; the public key is in the
  actor document as `<actor>#main-key`.
- **Rotation.** An admin can rotate one actor's key or all of them (after a suspected leak of
  `AUTH_SECRET` or the database); keys also rotate yearly. A rotation stores the new key, sends
  `Update{Service}` with the new `publicKey` to every follower inbox, and keeps the old public key
  in the database (not served) so a late delivery failure can be explained. Each rotation writes
  an `audit_log` row.
- **Inbound** signatures are verified against the sender's published key, fetched and cached; a
  verification failure refetches the key once (the sender may have rotated). Requests whose
  `Date` is outside a 12-hour skew window, whose digest does not match, or whose `keyId` does not
  belong to the activity's `actor` are refused.

### 5. Inbox: accept fast, verify and apply in the worker

`services/api/src/federation/inbox.ts` (new) does only cheap checks: content type, a body size
cap, the sender's domain against the block list (decision 7), a per-domain rate limit, and that
the activity is one of the handled types. It then stores the raw request for the worker and
answers 202. The worker verifies the signature (fetching the sender's key through
`resolveCallback`) and applies the activity:

- `Follow` of a federated channel: store the follower, send `Accept{Follow}` signed by the
  channel actor.
- `Undo{Follow}`: remove the follower.
- `Delete` of an actor: remove that actor as a follower everywhere.
- Anything else, including `Create` replies and mentions: accepted and dropped, never stored.

Why split it: every remote key fetch is an outbound request to a URL a stranger chose, and the
SSRF guard lives in the worker (`services/worker/src/webhooks/ssrf.ts`). Verifying in the worker
keeps the API free of outbound fetches and keeps one guard.

### 6. Followers are visible to the streamer and removable

Remote followers are rows in `federation_followers` (new: channel id, remote actor id, inbox and
shared inbox URLs, created time). The studio lists them (handle and server) to the streamer, who
can remove any of them; removal deletes the row and stops delivery. These are remote people's
handles, so they are never written to append-only columns (AGENTS.md) and are deleted, not kept,
when the follow ends. The streamer's data export carries the follower count, not the list: the
list is other people's accounts.

### 7. Moderation: domain blocks, mature labels, suspension

- **Domain blocks.** `federation_domain_blocks` (new) holds an instance-level list, edited on an
  admin page. A block matches the domain and its subdomains, refuses its inbox requests, drops
  its followers and stops delivery to it. Adding or removing a block writes an `audit_log` row
  with the domain and the acting admin's id.
- **Mature channels** federate with `sensitive: true` and a content warning (`summary`) from the
  i18n catalog, and send no thumbnail: remote servers are outside our 18+ gate, as avatars and
  panels are (`services/api/src/moderation/uploads.ts:11-12`). A `channel.update` that changes
  `mature` changes how later posts are sent.
- **Suspended channels send `Delete`** of the actor to every follower inbox, and the follower rows
  are removed. This needs an internal outbox event written by every suspension path (new,
  contract step), and the relay must hand internal events to the federation worker (today it
  only marks them published).

### 8. Delivery: outbox, worker, SSRF guard, backoff

`services/worker/src/federation/**` (new) turns `stream.online` (through N1's fan-out path), the
new VOD and clip events and the moderation events into signed deliveries, one per shared inbox
where the remote server offers one. Each delivery goes through `resolveCallback` (https only,
public pinned address) with the same backoff as webhooks. An inbox that has failed every attempt
for 7 days has its followers dropped. Delivery is at least once and objects have stable ids, so
remote servers dedupe.

### 9. Privacy

The followers collection publishes a count and no items. No object carries an email, an IP, a
user id of a local viewer or any viewer data. The actor and objects carry only what the public
channel page already shows.

### 10. In-house implementation

WebFinger, actor and NodeInfo documents, signing, verification and the inbox are written in the
repo on Web Crypto and plain JSON. Why: the surface we use is small and fixed, the libraries in
this space either pull a large JSON-LD stack or are young, and every dependency costs a
`vet-package` review and ongoing audits (rules 2 and 7). Interop is tested against fixtures
captured from Mastodon's documented shapes and against a second harness instance.

## Consequences

- N4 cannot start before N1's go-live fan-out (batch 4) and needs a contract step for the new
  events (VOD or clip public, channel suspended, and their reversals), the new tables and
  `FEDERATION_ENABLED`, plus a change to the outbox relay so internal events reach the worker.
- A suspended channel loses its remote followers for good: Mastodon treats a deleted actor as
  gone. If the suspension is reversed, remote people must follow again.
- Deleting a Note or Video asks remote servers to remove copies; it cannot force them.
- Remote people cannot reply, and their servers may show a reply box anyway. The actor
  description says replies are not read.
- A streamer can be followed from servers the instance has not blocked yet; blocks act after the
  fact.
- RSA keys and draft-cavage are older than RFC 9421; when the main servers accept RFC 9421 we can
  add it beside draft-cavage.

## Alternatives considered

- **Full federation (local users as actors, federated chat and follows, inbound replies).**
  Rejected for now: the moderation load is the reason, not the code.
- **`Person` or `Group` actors.** `Person` hides that posts are automated; `Group` (PeerTube's
  choice for channels) invites remote posting into the group, which v1 does not accept.
- **Push media to remote servers.** Rejected: storage and egress cost, and moderation actions
  could not follow the copies.
- **A library (Fedify or similar).** Larger surface and JSON-LD processing we do not need; can be
  reconsidered if scope grows.
- **Verify signatures in the API.** Needs an outbound fetch guard in the API too; one guard in the
  worker is simpler.
- **Ed25519 keys.** Smaller and faster, but Mastodon does not verify them for HTTP Signatures.

## Decisions at acceptance (2026-10-27)

The maintainer accepted the limited v1 as recommended:

1. Channels are actors that publish; local users do not federate.
2. `Note` for go-live; `Video` for VODs and clips, linking home; media is not pushed.
3. HTTP Signatures (draft-cavage) on all deliveries, with per-actor keys stored encrypted and
   rotated.
4. The inbox handles `Follow`, `Undo{Follow}` and `Delete` (actor) and ignores the rest.
5. Incoming follows are visible to and removable by the streamer.
6. Instance domain blocks with audit rows; mature channels federate with `sensitive: true`;
   suspended channels send `Delete`.
7. Delivery through the outbox and the worker with the SSRF guard and backoff.
8. Follower lists are not published; no IPs or emails in any object.
9. Implementation in-house (JSON-LD as plain JSON with the AS2 context), no library.
10. Why limited: inbound replies and follows from other servers bring moderation load we have not
    staffed for. Depends on N1's go-live event.

Decided by the head agent within these answers (recorded so reviewers can check them):

- Federation is off by default per instance (`FEDERATION_ENABLED`) and per channel.
- Actors are `Service`, with ids built from the channel id rather than the slug.
- Keys are RSA-2048 for interop; yearly and on-demand rotation, each with an audit row.
- Signature verification and activity handling run in the worker; the API inbox only does cheap
  checks and answers 202.
- Mature channels send no thumbnail; clips name no local user; removed media sends `Delete`.
- An inbox failing for 7 days loses its followers.
