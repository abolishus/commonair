## Build

1. **Server**: `services/api/src/main.ts` boots via `runService` on `API_PORT`: oRPC **OpenAPI handler** (`@orpc/openapi` `OpenAPIHandler`) under prefix `/api` (REST paths from the contract), oRPC **RPC handler** under `/rpc` (used by our web app), `GET /api/openapi.json` (generated with `generateOpenApi` from `@commonair/contracts/openapi`), better-auth handler under `/api/auth/*`, and the internal routes in `INTERNAL_ROUTES` (require `x-internal-secret` = INTERNAL_API_SECRET, constant-time compare). Readiness checks: Postgres, Valkey. CORS: only `PUBLIC_URL` and `AUTH_TRUSTED_ORIGINS` with credentials; bearer-token calls allowed from any origin without credentials.
2. **Context and access control** (one middleware driven by `ProcedureMeta`): resolve the caller from (a) better-auth session cookie or (b) `Authorization: Bearer <token>` looked up by SHA-256 hash in `oauth_tokens` (not revoked, not expired; update lastUsedAt at most once a minute). Enforce `access` (`public`, `user`, `owner` (channel owner or `editor` role on the channel named by the input's `channel` slug), `moderator` (owner/editor/moderator), `admin`, `treasurer`, `platform-moderator` (role moderator or admin), `relay` (relay registration token → relay_nodes.tokenHash), `overlay` (overlay token → overlay_tokens)). Token semantics (see `ProcedureMeta` doc): `scopes` undefined → session callers only (refuse tokens with FORBIDDEN); `[]` → any valid token; otherwise the token must hold every listed scope. Session callers act with full rights for themselves. `me.get` returns the email, so token callers additionally need `user:read:email` for it (refuse with FORBIDDEN otherwise; bots use `developer.tokens.validate` or `users.get` for their identity). Suspended/banned users are refused (FORBIDDEN) for writes. Bot accounts can only authenticate with tokens. Rate limiting: Valkey sliding-window per `meta.rateLimit` bucket (`default` 120/min, `write` 30/min, `auth` 10/min, `chat` 20/30s, `expensive` 5/hour) per user or IP hash; respond RATE_LIMITED with retryAfterSeconds.
3. **Auth (better-auth 1.7.10)** with the Drizzle adapter mapped onto our plural tables (`users`, `sessions`, `accounts`, `verifications`, `two_factors`, `passkeys`) and UUID ids (use uuidv7 from `@commonair/db`). Enable: email+password with required email verification, magic link, **passkey** (`@better-auth/passkey`), **two-factor TOTP** with backup codes, `username` plugin, `admin` plugin (roles map to our `platform_role` enum). Social providers Discord/Twitch/GitHub enabled only when both client id and secret are set. **Signup gates**: verify an **ALTCHA** proof-of-work solution (`altcha-lib`, HMAC key `ALTCHA_HMAC_KEY`; expose `GET /api/auth/altcha-challenge`); require `birthDate` and refuse anyone under `AUTH_MIN_AGE` (13) — do not store the date for refused signups; username = slug rules (`Slug` in common.ts), reserved names list (admin, api, www, mod, help, settings, etc.); record legal acceptances of the current required documents (accept `acceptedDocumentIds`). On signup also create the user's `channels` row (slug = username, displayName = name) in the same transaction (via better-auth database hooks). Emails (verification, magic link, password reset, 2FA enabled notice) are sent through a `Mailer` interface you define in `services/api/src/mail.ts` with a nodemailer SMTP implementation (plain text + minimal HTML is fine; a later unit swaps in React Email templates from `@commonair/email`). From address: `MAIL_FROM` or `"<instance name> <noreply contact>"` from `instanceSite()`.
4. **Procedures to implement fully now** (everything else in the contract must exist and throw `ORPCError("NOT_IMPLEMENTED")`-style — use code `NOT_IMPLEMENTED` with HTTP 501 — so the router type-checks completely and later units fill them in their own files):
   - `instance.info` (source link via `sourceLink(instanceSite(env))`, version from package.json, enabled features from env), `instance.status` (component health of postgres/valkey/mediamtx/chat/origin from readiness probes; incidents from `incidents`).
   - `me.*` except `exports`, `deletion`; `me.bots.*` (bot accounts: `accountType = bot`, `botOwnerId`, no password; tokens minted as personal tokens in `oauth_tokens` with appId null).
   - `users.get`, `categories.*`, `admin.categories`, `admin.setRole`.
   - `directory.*`: fair discovery per the `discovery.ranking` governance setting: `home` returns `spotlight` (rotating slots for live channels at or under `spotlightMaxViewers` verified viewers, rotation deterministic per `spotlightRotationMinutes` window, never the same channel in consecutive windows when alternatives exist), `newAndLive` (channels created within `newChannelMaxAgeDays`), `live` (blended score: weights.viewers × log-scaled verified viewers + freshness + followMomentum + smallChannelBoost; document the formula in `services/api/src/discovery/README.md` and expose it via `directory.ranking`), `following` for signed-in users; `random` (uniform over live channels matching filters); `search` (Postgres full-text on channels using the `channels_search_idx` expression + category name ILIKE). Mature streams excluded unless `includeMature` AND the caller is a confirmed adult. Every StreamCard carries `reason`.
   - `channels.get/update/setPanels/uploadUrl/follow/unfollow/followers/roles.*` — follow writes the outbox event `channel.follow`; follower counts kept in `channels.followerCount` transactionally; follow rate limits (max 30/min per user) and a channel-level setting-free account-age gate are left to integrity, but refuse following yourself. `uploadUrl` presigns to `S3_BUCKET_MEDIA` under `channels/<channelId>/<purpose>/<uuid>`.
   - `stream.ingest` (RTMP + WHIP URLs from env, recommended encoder settings: H.264 high, AAC 160 kbps, 1080p60 6000 kbps CBR, keyframe 2 s, plus notes), `stream.obsConfig` (OBS `services.json`-style custom service with server and recommended settings — do not embed the key), `stream.keys`, `stream.rotateKey` (secret `randomSecret("live_")`; store sha256 + prefix; returned key string is `<slug>?key=<secret>` exactly as OBS needs; revoke the previous active key), `stream.health` (from `broadcast_health_samples`, `KEYS.renditions`, `KEYS.simulcastStatus`, viewer counts), `stream.simulcast.*` (stream keys encrypted with `encryptSecret(AUTH_SECRET, "simulcast", key)`; never returned).
   - **Stream-key leak detection**: a pure scanner function `findLeakedKeys(text)` that matches the `live_` prefix pattern, and an endpoint-free hook used by chat later: if a chat message or panel contains a channel's active key, revoke it and notify the owner (implement the API-side `revokeLeakedKey(secret)` function and use it in `setPanels`/`update` description).
   - **MediaMTX hooks** (`INTERNAL_ROUTES`): `mediaAuth` handles `MediaMtxAuthRequest`: `publish` on `live/<slug>` requires the stream key (RTMP: `key` query param; WHIP: bearer `token`) to match the channel's active key hash and the channel/owner not suspended; `read`/`playback` require user `MEDIA_INTERNAL_USER` + password INTERNAL_API_SECRET (only our origin/media services read MediaMTX directly; viewers go through the origin); `api`/`metrics` same internal credentials; everything else 401. Return 200/401 only. `mediaReady`: create the `broadcasts` row (title/category/mature copied from the channel), set `channels.liveBroadcastId`, record `streamKeys.lastUsedAt`, write outbox `stream.online`, publish `LiveEvent` online on `BUS.live`. `mediaNotReady`: end the broadcast, clear liveBroadcastId, outbox `stream.offline`, publish offline. Idempotent and safe under duplicate/out-of-order hooks.
   - `playback.start/heartbeat/end`: create `playback_sessions` (hash IP and deviceId with `hmacHex(AUTH_SECRET, …)`; never store raw IP), assign the delivery source: if active relays exist in `KEYS.relays` with spare capacity, assign a share of new sessions to relays weighted by capacity (deterministic weighted pick, origin keeps at least 1/(N+1)); if `CDN_PROVIDER=origin-pull` and the channel's verified viewers exceed `CDN_BURST_VIEWER_THRESHOLD`, assign CDN; else origin. Sign a `PlaybackClaims` token (TTL `PLAYBACK_TOKEN_TTL_SECONDS`) with `PLAYBACK_SIGNING_KEY`; playlist URL = `<PLAYBACK_PUBLIC_URL, relay publicUrl, or CDN_BASE_URL>/hls/<path>/index.m3u8?t=<token>`. Native HLS clients (WebKit) get `p2p.enabled=false`. Heartbeats update the session row (watchSeconds, bytes, stalls, latency, ttff), the `KEYS.viewers` ZSET, and refresh the token before expiry; validate that the token matches the session; reject heartbeats for ended sessions. Compute public viewer counts as sessions with a heartbeat in the last 30 s whose verdict is `verified`; until the integrity unit lands, a session becomes `verified` after 3 consistent heartbeats (playedSeconds ≈ wall clock between heartbeats ±50%, visible or unmuted at least once) — put this rule in one small replaceable module `src/playback/verify.ts`, and never count `excluded` sessions. Cache counts in `KEYS.viewerCount` (5 s TTL).
   - `chat.history`, `chat.settings`, `chat.updateSettings` (writes `channels.chatSettings`, outbox `channel.chat_settings.update`, publishes to `BUS.chatControl(channelId)`), `chat.bans.*` (writes chat_bans + mod_actions + audit_log + outbox `channel.ban`/`channel.unban`, publishes to `BUS.chatControl`), `chat.filters.*`, `chat.emotes.*`, `chat.connectToken` (`signChatToken`; anonymous gets uid null and scopes ["chat:read"]; URL = `CHAT_PUBLIC_URL` from coreEnv).
   - `relays.mine/create/remove/register/heartbeat/adminList/reinstate`: registration token `randomSecret("relay_")` hashed; `register` stores publicUrl, key, capacity; health-check the relay (`GET <publicUrl>/healthz` with 3 s timeout) before marking `active`; heartbeats update `KEYS.relays`. `relays.receipt` may be implemented minimally (verify signature with `verifyReceipt`, check nonce uniqueness, store `pending`) — cross-checking is done by the worker/integrity units later.
   - `developer.tokens.validate` (Twitch-compatible shape).
5. **Outbox helper**: `services/api/src/events/outbox.ts` `emit(tx, type, channelId, payload)` validating payloads with `EVENTS[type].payload` and inserting into `events` in the caller's transaction. Never publish directly from request handlers except `BUS.chatControl`/`BUS.live`.
6. **Audit helper**: `audit(tx, {actorType, actorId, action, subjectType, subjectId, channelId, reason, details})`.
7. **Error mapping**: Zod validation → BAD_REQUEST with issues; DB unique violations → CONFLICT; never leak SQL.
8. **Code layout**: one file per contract namespace under `services/api/src/routes/` (`instance.ts`, `me.ts`, `users.ts`, `directory.ts`, `channels.ts`, `stream.ts`, `playback.ts`, `chat.ts`, `relays.ts`, `developer.ts`, `money.ts`, `bot.ts`, `interact.ts`, `coop.ts`, `integrity.ts`, `appeals.ts`, `safety.ts`, `legal.ts`, `admin.ts`, `vods.ts`, `clips.ts`), assembled in `src/router.ts`. Later units will each take over specific route files, so keep cross-file coupling low (shared helpers in `src/lib/`).

## Security notes

- Checkout `returnPath` is relative-only (contract `ReturnPath`); build absolute URLs from `PUBLIC_URL`.
- Never put personal data into append-only columns (audit `details`, ledger text): ids only (AGENTS.md, ADR 0004).
- Governance settings are changed only through the proposal flow; read them, never write them (the DB refuses).
