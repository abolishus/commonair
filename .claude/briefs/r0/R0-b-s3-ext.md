# R0-b: an external S3 store instead of Garage

You are implementing unit R0-b for CommonAir (repo: /Users/joshe/Repos/bcon). Read AGENTS.md,
PLAN.md and docs/architecture.md first, then `.claude/briefs/next/R0-release.md`,
`.claude/briefs/next/S1-scaling.md` (S1-b builds external Postgres and Valkey on what you build),
`.claude/briefs/r0/README.md`, [ADR 0023](../../../docs/decisions/0023-release-and-self-hosting.md)

the repository. Work in your own git worktree on a branch named `r0/b-s3-ext`.

## Why

Garage on the same disk is the FOSS default and stays so. But an operator whose disk dies loses
every object with it, and our own instance moves objects to DigitalOcean Spaces at S1 stage 1.
`selfhost.sh` must be able to point a self-hosted instance at **any** S3-compatible store
(Spaces, AWS S3, Hetzner Object Storage, MinIO, a Garage cluster elsewhere), with no provider
special-cased (AGENTS.md non-negotiable 3, ADR 0025 decision 1). This is also the pattern S1-b
follows for external Postgres and Valkey, so make it a clean, general mechanism.

## Build

1. **The choice.** `--s3-endpoint <https url>`, `--s3-region <r>`, `--s3-path-style true|false`,
   `--s3-public-endpoint <https url>` (default: the endpoint), and the four bucket names
   (`--s3-bucket-media` etc., defaulting to today's names). Keys never go on the command line
   (they would show in `ps`): read `S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY` and the evidence pair
   from the environment or prompt for them, and store them in the 0600 env file like every other
   secret (the reason is in `env_set`'s comment, :143-146). Validate every value as the existing
   validators do. Persist the mode (`S3_MODE=garage|external` or equivalent) so `upgrade` keeps it;
   switching mode on an existing instance is refused with a message unless an explicit
   `--migrate-objects` path exists (it does not: say so, and point at the object copy in
   `backups.md`).
2. **Units read the endpoint from the env file.** Move `S3_ENDPOINT`, `S3_REGION`,
   `S3_FORCE_PATH_STYLE` (and WAL-G's endpoint) from `Environment=` lines into the per-unit key
   lists, with `configure_env` writing the Garage values in Garage mode, so both modes go through
   one path. `backfill_env` writes them for existing installs on upgrade.
3. **External mode installs no Garage.** Neither `commonair-garage` nor its volumes. Services
   still need a dependency that means "storage is ready": design it (for example a
   `commonair-storage-init` one-shot that bootstraps Garage in Garage mode and, in external mode,
   checks with the configured keys that each bucket exists and is writable, then exits). Buckets
   on an external store are the operator's to create (with CORS on the media bucket for presigned
   PUTs from the browser origin); `storage-init` fails with a message naming what is missing.
   Keep the unit rename upgrade-safe: an upgrade from rc.2 must stop and remove the old
   `garage-init` unit cleanly (`install_units` already deletes `commonair*` files the release no
   longer ships).
4. **Caddy.** In external mode the browser talks to `S3_PUBLIC_ENDPOINT` directly, so the Caddy
   S3 route must not proxy to a Garage that is not there: make the upstream come from the env
   (`{$S3_UPSTREAM}` or similar) or drop the route in external mode. Explain the choice; same-origin
   uploads via Caddy to an external HTTPS store are an option if the CSP change is heavier.
5. **WAL-G.** In external mode, WAL-G's default prefix uses the external store too, unless the
   operator set `AWS_*`/`WALG_S3_PREFIX` (they may want backups in another region; that is
   ADR 0025's setup and must keep working).
6. **`status`** says which store is in use and, in external mode, checks reachability of each
   bucket (HEAD with the instance's keys, from the tools image) without printing keys.
7. **Docs.** `configuration.md`: the new flags and keys. New `object-storage.md`: requirements for
   an external store (S3 API features used: presigned PUT/GET with SigV4, multipart if used,
   path or virtual-host style, CORS for the media bucket), how to create the buckets and a key
   limited to them, and DigitalOcean Spaces as the worked example (endpoint
   `https://<region>.digitaloceanspaces.com`, path style false, CORS per bucket, only `private`
   and `public-read` ACLs, SSE-C only). Mention that a droplet resolving Spaces through the VPC
   resolver is not billed for that transfer.
8. **e2e checks** in `scripts/selfhost/e2e-s3.ts`, as functions taking the e2e helpers
   (`type InHost = (script: string, opts?: { user?: boolean; env?: Record<string, string>; allowFail?: boolean }) => string`,
   `type Expect = (ok: boolean, what: string) => void`, the shapes in `e2e.ts:100-145`):
   - `externalStoreSetup(inHost, expectThat)`: start a second Garage (or MinIO, if its license and
     image are already allowed: check `infra/image-licenses.json`; otherwise Garage) in its own
     container on the host **outside** the instance's network, create the buckets and CORS.
   - `checkExternalStore(inHost, expectThat)`: after an install with the external flags, no
     Garage unit exists, an avatar-sized object round-trips through the browser upload path, the
     export link works, `status` reports the store.
     R0-e decides where these run (a second install phase or a separate e2e variant).
